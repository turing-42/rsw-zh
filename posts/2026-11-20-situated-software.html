情境软件

Situated Software

Clay Shirky · 原文 Tue, 30 Mar 2004 00:00:00 GMT · 译于 2026-11-20

本文最初发表于 2004 年 3 月 30 日「网络、经济与文化」（Networks, Economics, and Culture）邮件列表。

订阅该邮件列表。

我在纽约大学交互电信项目（ITP）教书。那里学生大致一半是关心美学的技术人员，一半是不怕机器的艺术家，因此是个观察未来的好地方。

我认为自己看到的未来之一，是软件生态正在发生变化，我暂时把它叫作「情境软件」（situated software）。这是为某个具体的社会情境或场合而设计、也在其中使用的软件。这种做软件的方式，与我所谓的「网络学派」（Web School，我学编程时的那套范式）形成对照——后者把可扩展性、通用性和完整性奉为关键美德。

我看着自己的学生高高兴兴地无视网络学派的种种规矩，却做出了有意思的东西。这件事让我整整一年都处在认知失调之中，所以我想把这种模式描述出来，哪怕它还只是雏形，也好看看别人是否在别处见到了同样的事。

以「打」计的用家 企业式的设计实践与「小件松散拼装」（small pieces, loosely joined，借 David Weinberger 的妙语）之间，一直存在张力。后者的好处，部分已在《更糟即是更好》（Worse is Better）和《大教堂与集市》里说过。情境软件属于「小件」这一类，另有如下特征：它是为某个特定社会群体设计，而不是为一组泛泛的「用户」设计。

与经典 Web 应用相比，这带来的最大差别是：为几十个用户开发应用变得容易了，而在当下的设计实践里，这是个荒谬的目标人群。为小群体量身定制软件，向来是银行和实验室的领地——因为成本所限，网络学派的应用一直集中火力争取大规模受众。而一旦把规模带来的价值置于优先地位，其他种类的价值、尤其是社会性的价值，就被推到了够不着的地方。

我们用「这没法扩展」掐掉了多少关于软件的对话，久到已经忘了扩展性问题本来并不致命。N 平方问题只有在 N 大时才是问题，而在社会情境里，N 通常不大。读书会五个人比十五个人好用；讨论课十五人比二十五人好用，更别说五十人。

这样一来，为特定群体量身定做的软件就有了一些讨喜的性质：造得更便宜更快，扩展性问题更少，目标用户也更可能真的用起来。它也有几个明显的缺点：出了原生环境就不太有人用；日后若被要求应付更大的群体，会格外脆弱；寿命可能更短。

但我确实看到学生在做这类取舍，因为网络学派当初要对付的种种稀缺——够用的硬件太贵、编程人才难找、潜在用户分布太稀——已经不再是原来的约束。

逃跑的老师们 我第一次隐约觉得网络学派的理由在松动，是两个以前的学生 Paul Berry 和 Keren Merimeh 写的一个应用。2002 年 11 月，作为一门研究在线空间之感受、名为「社会天气」（Social Weather）的课的作业，他们做了一个应用，名字（相当惊悚）叫「逃跑的老师们」（Teachers on the Run）。

Teachers on the Run 本质上是给 ITP 教授们做的 HotorNot，让学生们赶在春季选课之前描述并评价我们。每位教授都列在数据库里；学生可以匿名上来，写一条关于某位教授的评论，或者投票赞成／反对已有的一条评论。评论按票数总和排序，所以一条 +5 的评论（赞成比反对多五票）会排在 +2 或 -3 的上面。就这么简单——一串名字，一串评论，点击投票，一个排序算法。

他们在一个周五上线。到周六晚上，另一个学生打电话到我家，说我最好去看看。ITP 总共才两百来个学生，可 Teachers on the Run 已经攒了数百条评论，多数是好评，有些是差评，还有几条可能构成诽谤。但更要紧的是，二十四小时里已经有一千多票。到周一早上，有学生告诉我他们知道那网站上有什么，不是因为看过，而是因为整个周末所有人都在谈这件事。

Teachers on the Run 让我觉得奇怪的地方是：它做成了网络学派版本做不成的事。RateMyProfessors.com 已经上线好几年，功能之齐全，足以让 Teachers on the Run 那套简陋的写／读／投票羞得抬不起头。可 ITP 从来没人费心去用 RateMyProfessors.com，尽管那个周末的评分投票狂欢已经说明需求一直都在。

尽管它释放出那么大的社会能量，我当时却错过了 Teachers on the Run 的重要性。我对自己解释说，它成功的原因多少有些不公平：用户认识写程序的人；名字数据库是事先填好的；写程序的人可以用内部邮件列表来发布应用，而不必靠新闻稿和横幅广告去求关注。最要命的是，它没法扩展——而不可扩展，就不算成功的 Web 应用。死定了，证毕。

后来我看到了我最近那班学生经历的设计过程。

这门课 去年秋天我教一门叫「社会性软件」（Social Software）的课，学生分组设计并发布软件，用来支持某种形式的群体互动。为了把课程落到实处，我要求他们做出来的东西必须给其他 ITP 学生用。这条规矩的一阶好处很简单：设计者与用户出自同一个人群，因此可以把自己的直觉当作可靠的依据；测试者顺着走廊走一圈就能招到；而且它能挡住那些想「把大海煮沸」的空想。

我没料到的是二阶好处。小组一次又一次撞上问题，而他们的解决办法，多少都靠动用了网络学派信徒拿不到的社会基础设施或情境敏感信息。有两种策略尤其突出。

第一种与声誉系统有关。一个项目叫 The Orderer（设计者 Vena Chitturi、Fa-yi Chou、Rachel Fishman、Cindy Yang），用来协调集体订餐——深夜赶工时很常见。另一个叫 WeBe（Brandon Brown、Yoonjung Kim、Olivier Massot、Megan Phalines），是协调集体采购薯片、电机之类东西的工具。因为牵扯到钱，网络学派的做法总得给出对付赖账的手段，比如预付款、托管账户，或者正式的声誉系统。

而这两个项目里，学生们的决定是：既然用户都是 ITP 共同体的一员，那就干脆把赖账的人标出来，以公开姓名相威胁就够了。在共同体面前丢脸的可能性，成了应用设计的一部分，尽管那个共同体、以及那顶多算是虚张声势的羞辱，都在应用本身的框架之外。

共同体的注意力 另一种策略与共同体的注意力有关。另外两个项目，Scout（Karen Bonna、Christine Brumback、Dennis Crowley、Alex Rainert）和 CoDeck（Mark Argo、Dan Melinger、Shawn Van Every、Ahmi Wolf），则以更字面的方式把应用安置在共同体之中。Scout 显示的是物理在场：学生可以把自己登记为正在 ITP 楼层的某处，系统再把这些信息展示出来。CoDeck 是一台社区视频服务器，为的是让影像艺术家彼此分享作品、互相评论。

两组都撞上了经典的「通知」难题——想让用户来看，就得打断他手头正在做的事，而用户向来不喜欢被打断。网络学派的应用为此烧掉了数十亿美元，它们假定用户会加书签再回访，或者乐于接受邮件提醒；但除了 Schwab.com 和 eBay 这类少数被大肆宣传的成功案例，用户大多拒绝「常回来看看」。

Scout 和 CoDeck 想到的是同一个办法：把界面的大部分从 PC 那块与人分离的屏幕上拿下来，搬进休息室里的一件实物——休息室是 ITP 楼层中央的会面处、饭堂兼桌上足球场。两个项目都在休息室里搭了带实体界面的信息亭，代替键盘和鼠标。Scout 用条码阅读器刷卡签到；CoDeck 掏空了一台七十年代中期的 BetaMax 机壳，塞进一台 Linux 机器，再用 BetaMax 的按钮让用户控制视频流。两者都有网站，用户可以在上面录入或取回数据，但各自的核心，是把应用放进社会情境里的那个物理位置。

这些项目都接住了课程最初那句箴言——应用必须对共同体有用——并且开始使用它的推论：共同体也必须对应用有用。

群体的能力 在软件设计里，我们不断依赖个体的认知能力：我们假定用户能把鼠标和光标联系起来，假定图标会传达信息。但我们很少依赖群体的认知能力，尽管在现实世界里我们一直在依赖它。

头脑风暴时，一群人不仅比各自单干产生更多想法，还能产生更多种类的想法；群体的共识，往往比群体里最有见识的那个人的判断更准。群体对自己的了解也很多。工作小组里的人知道该找谁问设计意见，紧急时谁靠不住，用不着把这些角色正式规定下来。社交圈里的人知道跟谁喝酒有意思、钱不该借给谁（往往是同一个人），不需要把这些知识写进常见问题解答。

网络学派的软件无视这类知识，因为它难以明说。比如在大多数大型邮件列表上，只有少数人会发起讨论，多数人只是跟帖；再往上一个层次，只有少数成员发过言，多数人只是潜水。这些模式我们几十年前就知道了，可邮件列表软件至今没有提供任何区分「发起」与「延续」话题的功能，也不区别对待高产发帖者和潜水者。

不过还有另一种策略，相当于要求用户认出图标：设计者直接假定群体具备某种能力，不必用代码把它复述一遍。如果公共采购池里有人没交钱，软件可以甩出一条消息：「有人赖账，处理一下。」现实中的群体会自己想办法解决，通常靠道德劝说，或者靠损失声誉资本的威胁，极端情况下把人排除在外。

这与线下群体每天都在发生的事没有区别，可放到网络学派的语汇里，这个办法是错的，因为那些 Web 应用不能假定存在一套心照不宣的声誉系统。依靠既有的社会结构，情境软件注定做不到网络学派应用那样的规模；但也正因为如此，它能做到网络学派软件做不到的事。

外人的眼睛 我真正开始把情境软件当作一种可行的开发策略、而不是「真正的」应用开发的退化形态，是在我请了外面的评审来给「社会性软件」课上期中点评的时候。这些人全都以社会性软件为业，那次点评极有价值。但评审提出的两条建议，让我觉得好笑。

第一条是给 CoDeck 组的：他们应该把视频工具的所有功能都搬到网页上——上传、下载、评论等等。第二条是劝 WeBe 组去看看 Mercata、MobShop 这类网络学派的团购网站，拿它们当自己工作的参照。

就是这一刻，我的认知失调终于撑不住了。那两条意见，a) 如果我是在别人课上做外聘评审，一字不差也会这么说；b) 放到两个组各自面对的问题上，显然是错的。

关于 CoDeck 应向普通网页开放的建议，是以反问的形式提出的——「为什么不做得尽可能普及呢？」在网络学派里，答案当然是「没理由不」，因为用户总是越多越好；但对 CoDeck 来说，不把项目变成网页视频应用，有好几个充分的理由。

第一，界面的实体化——那台掏空的 BetaMax——提供了共同体可感的可供性，在网页上根本无法复制。第二，CoDeck 服务的是一个紧密的共同体，一旦对所有人开放，ITP 影像作者之间的交流密度就会被稀释。第三，把视频机放在休息室里，它就能自我约束：共同体的凝聚让它基本免于滥用；而一个对所有人开放、无需密码的「上传并点评」视频网站，几小时之内就会沦为色情垃圾场。最后，服务本地共同体能最大限度地利用局域网里的免费带宽，从而提供一些功能；这些功能若放到公共系统上，光是成本就能把系统压垮。

WeBe 之小 同样，建议 WeBe 去参考 Mercata 和 MobShop，背后是这样一种假定：最终目标应当是在大规模上运作。可 Mercata 和 MobShop 之所以失败，恰恰因为它们是为规模而造的。

那些网站需要一个良性循环：用户越多，省得越多；省得越多，用户越多。可惜，「某地某人正在特百惠上省下一大笔」这个念头，从来不足以吸引用户；没有临界规模，良性循环就翻转成恶性循环。和 RateMyProfessors.com 一样，光是存在一个网络学派应用并不够；而它既是按几万名用户造的，就没法为几十人甚至几百人运转。

另一方面，WeBe 复制的是一个小组规模的模式——他们最早在同班同学 Scott Fitzgerald 那里看到。他张罗了一次 Max 多媒体剪辑软件的三十份授权团购：用 ITP 邮件列表招募买家，然后在楼层里转着圈拧人胳膊、收支票。这需要真实的社会结构才能成立——人人都认识并信任 Scott。

作为发起人，Scott 也收获了善意：参与者人人都省了不少钱，他的名声因此更好。与真正的资本不同，声誉资本在更小、更封闭的社会系统里更容易积累。WeBe 的想法部分源自 Scott 的一句话：那次团购虽然成功，但太费劲了。WeBe 组只要能让 ITP 的团购省点事就行；他们不必自己搭身份系统或声誉系统。因为软件就安置在一个特定（而且格外紧密）的共同体里，这些东西是白送的。

旧的稀缺在消退 网络学派之所以在某些地方行得通，是因为它是对某种稀缺的恰当回应。资金的稀缺：服务器很贵，更别提负载均衡路由器、磁带备份，以及维持正经可用率所需的其他家当。人才的稀缺：好程序员难找，顶尖程序员更是凤毛麟角。使用的稀缺：用户很忙，是习惯的动物，而争夺他们注意力的竞争者众多。

可是，应付这些稀缺会让网络学派的设计带上一种旋转木马的味道。你需要扩展，因为做一个有用的 Web 应用太贵；而大部分开销恰恰来自对规模的要求。更糟的是，这些稀缺彼此放大：要造一个能扩展的应用，你得有大笔硬件预算；要扛住负载，你得有好程序员和系统管理员，他们的薪水需要更高的市场预算；而要吸引足够多的用户，来支付这一切。

我认为我看到学生们在做的，就是从这匹旋转木马上下来。他们能这么做，是因为网络学派所应付的那些稀缺，都不再像过去那么要命了。首先，摩尔定律及其在存储上的对应物，加上操作系统的逐步改进，意味着一台八百美元的台式机开箱就能当一台相当好的服务器。

其次，用户注意力之所以稀缺，部分是因为用户本来就很少。九十年代在 Web 上发布应用，意味着放弃与某个现实共同体建立直接联系的机会，因为互联网用户分布得太稀，而且在 IT 行业之外，多数现实群体只有一部分成员在线。

那样的日子正在结束，有些地方已经结束了。今天的美国，如果你不到三十五岁，或者年收入超过三万五千美元，你大概在上网；如果这两条都成立，那么你认识的人多半也都在上网。现在你可以为一个现实中的群体发布应用，并且确信他们全都能上网。

编程的性质，以及 MySQL 的古怪案例 最后，编程这门实践正在变化。Gartner 最近一句话引起骚动：十年后，美国的程序员会减少二十三万五千人。这就好比在八十年代预言，到 2004 年美国打字员会变少。这个预言在某种意义上会成真——办公室的打字组消失了，大量数据录入工作搬到了海外。但真正的打字——手指敲击键盘——并没有消失，它扩散到了所有地方。

编程也是如此。尽管注意力全被外包吸走，同时也有大量的「下放」（downsourcing）在发生：编程从一份职位描述，变成一项被更广泛实践的技能。如果我们说的「程序员」指「写代码的人」，而不是「靠写代码拿钱的人」，那么到 2015 年，程序员的数量会上升，大幅上升，尽管很多在用 Perl、JavaScript 和 Flash 的人并不把自己看作程序员。

推动这件事的技术很多——Perl、PHP、ActionScript、DHTML——混搭着用，没有哪个核心工具，只有一个奇怪的例外。我见过的这类应用，无一不用 MySQL 数据库。

这里可以拿 Web 服务器软件作类比。九十年代中期，把一台 Web 服务器跑起来本身就是个项目目标，过程如此混乱。后来 Apache 出现了，把流程简化到 Web 服务器成为搭建更大东西时的一块普通积木。

MySQL 为数据库做了同样的事。这对群体应用的发展很重要，因为「能排序」是一种公共品。如果 Teachers on the Run 只是把教授的名字和评论列在一起，它就是个只能写的应用，像新闻文章底下那些毫无用处的「告诉我们你怎么想！」评论框。任何群体都想知道的一件关键事情是「别人都怎么想？」，尤其当有理由相信群体整体比任何个人知道得更多时。加上「用户给评论打分」的机制，再按分数而非时间取数据，系统才变得有价值。

你当然可以用别的办法做出这类功能，但 MySQL 让这活儿轻松得多，轻松到用过 MySQL 之后，它已经变成了另一种活儿。关于用 MySQL 还是别的数据库，有各种复杂的技术争论，可那些争论如今都不重要了。不管原因是什么，MySQL 似乎成了这一批新应用的核心工具。

给你妈做的软件 情境软件与其说是一种技术策略，不如说是一种态度：在意软件与其用户群体之间的贴合程度，并且拒绝把规模、通用、完整当作无条件的优点。这样看，网络学派软件对「个性化」的执念，是在为人尽皆知的真相赔不是——多数 Web 应用在设计上就是非个人的，因为它们是为泛泛的用户造的。让用户自定义网站界面也许会让它更有用，但并不会让它更「个人」，就像 ATM 一边吐钱一边把你的名字打在屏幕上，也谈不上个人。

相比之下，情境软件不需要「个性化」——它从诞生起就是个人的。Teachers on the Run 就是这样运作的。人人都知道是 Paul 和 Keren 做的。你能评价的只有 Clay、Marianne、Tom 和其他 ITP 教授。你甚至不知道它存在，除非你在那个 ITP 邮件列表上。换句话说，这个应用缺乏通用性和完整性，这本身传达了一件事——「这是我们为你做的」——而 RateMyProfessors.com 那张非个人的脸既没有、也装不出来。

我一个学生提到，他给母亲——一位学校老师——做了个 Web 应用来管理她的班级。如果你是单干、无偿、用业余时间，你绝无可能做出一个满足各地教师通用而完整需求的应用。但你可以给你妈做一个。

小而专用的应用一直都存在，当然——学 BASIC 曾是 PC 拥有者的成人礼，投资银行和实验室这类数据密集的机构也会为小群用户写软件。但现在，好用的工具、有本事的用户，加上作为社会舞台的互联网，这三者相加，让造这类软件更简单，成品质量更好，送到用户手里只需点一下链接。以十来名用户为中心的设计，过去难以为继，如今可能成为常规做法。

接下来呢？

那么接下来会怎样？如果我看到的不是暂时的现象，也不局限于一小撮情境，那么这类小巧贴身的应用会多起来。这会带来一些明显的坏处，包括把这类应用的开发者拴在社区支持的角色上，以及缩短以这种方式造出的软件的可用寿命。

不过，对长寿的期待只是规模在时间上的版本——我们假定应用应该长期管用，部分是因为造它太贵。可一旦把应用拼起来变得又便宜又容易，这个理由就弱了。企业经常让一群高薪的人花上几百个小时，做一份只在一次会议上被看一眼的 PowerPoint。软件应该为很多用户而造、或者应该用很多年，这些是文化上的假定，软件本身并不要求。

事实上，就实际效果而言，多数为大量用户而造、或设计成永久使用的软件，两个目标都没达成。情境软件是在说：「多数软件只得到少数用户，只用很短一段时间；何不干脆照这个事实来设计？」

说来奇怪，这是一种进步，不是因为情境软件会取代其他类型的应用，而是因为它基本不会。眼下这套软件生态给了我们很多价值，却不包括「为一个只有几十人的群体造一个只用几个月的应用」。可现在，我想我们开始看到一个新的软件生态位：共同体得到为极具体需求定做的工具；这些工具在以往多数设计质量或成功的检验上都通不过，却运转良好，因为它们极其贴合使用它们的那个共同体。
